# CaseHUD in CouchHUD

[CaseHUD](https://github.com/kewe87/CaseHUD) shows temperatures, load and more on the LCDs in fans and pump heads. It is a **separate program** with its own local API; CouchHUD contains no code from it. CouchHUD can install it along, start it and fully control it from the sofa.

## Usage

*Settings › CaseHUD › Open CaseHUD.* Depending on the state the page shows:

- **Not installed:** a short description and *Install*. Windows asks once for administrator rights, because the setup installs a sensor service and a driver (PawnIO). Progress and errors appear at the top of the page.
- **Installed, not started:** *Start* (CaseHUD then runs in the background in the tray) and *Open on PC*.
- **Running:**
  - **Displays** as tiles with live preview (every 3 s, only while the page is in front). A opens the display: *Design* (grid with preview images, only designs in the display's resolution; X filters by set, Y by theme), *Brightness* and *Rotation* (left/right), *Mode* (display, media, off), *Identify* (X, the display blinks briefly).
  - **For all displays:** displays on/off, choose a *scene*, automatic scene switching on/off, next scene, *Set for all displays* (one style with one click), import community designs, AWTRIX on/off, identify all displays, *Open on PC (editor)* for the design editor.
  - **Status:** sensors, game mode, version. If a newer version exists, *Update to x.y.z available* appears at the top.
  - **First start (CaseHUD 1.0):** until the notice in the CaseHUD window is confirmed with "Understood", CaseHUD talks to no device. If the status reports `disclaimerAccepted: false`, the page shows the card *Open CaseHUD once and confirm the notice* (opens the window via `POST /gui/open`); displays and sensors show as "not available yet" until then, not as an error. The notice can only be confirmed there; CouchHUD never tries it through the API. If the field is missing (older builds), that counts as "unknown", not as "not confirmed".
  - **Lighting (CaseHUD 1.0):** only if the status contains `lighting: {enabled, active}` (otherwise `/lighting` does not exist and the row is missing). On/off, brightness, effect (only those delivered as `featured`; name from `labelDe` on the German interface, otherwise `label`, otherwise a translation for the seven known ones, otherwise the raw name), the effect's parameters by type (number with left/right in steps of `step`, without `step` one twentieth of the range; color from a palette; switch; selection list; text and numbers without a range are view-only; labelled like the effect) and devices on/off with their state (conflict, error, message from CaseHUD) for viewing. CaseHUD lists devices only while lighting is on. Brightness, effect and parameters can also be set before switching on. If CaseHUD answers switching on with 409 `ack_required` (nothing was applied), the page asks whether to open the CaseHUD window (confirm once there under "Lighting"); 403 `gui_only` likewise. CouchHUD does not show controller settings and "ignore conflicts", only the note "Only in the CaseHUD window under Lighting".
  - **Values that end up in flash** (brightness and rotation of a display, brightness and step values of the lighting): left/right changes only the display; the value is sent when 700 ms pass without input, or immediately with A. CaseHUD also merges writes itself (at most one per second).
- **Guide menu** (while CaseHUD runs): *Case displays off/on* and *Next display scene*.

**Expert mode** (Settings › CaseHUD): the setup options for the next install or update (*start with Windows*, *FPS detection*) and *Report games to CaseHUD*. In simple mode the defaults apply: start with Windows on, report games on, **FPS detection off** (it adds you to the "Performance Log Users" group and takes effect only after the next sign-in). The confirmation dialog before installing names the exact version and everything the setup installs: sensor service, driver, autostart and, if applicable, the group.

## Couch lock

With the couch lock active, only these work without a code: viewing status and lighting, choosing a scene or switching to the next one, displays on/off and identifying displays. Everything else (designs, brightness, sets, rotation, changing lighting, community import, AWTRIX, installing, starting, opening the editor) requires unlocking. The rule lives in one place (`CaseHudPolicy.OpenWhileLocked`) and applies in the host, not only in the interface.

## How it works

| Part | Where |
|---|---|
| CaseHUD is found through `%APPDATA%\casehud\api.json` (port, token, process). CouchHUD checks that the process ID really is `CaseHUD.exe` from the given path (after a crash the file can be stale). The installation is recognized by the uninstall entry (`{6F3A9C2E-5B71-4C0D-9E8A-CA5E0D1A2B30}_is1`, 64-bit registry). | `Integrations/CaseHud/CaseHudDiscovery.cs` |
| Started with `CaseHUD.exe --background` (without a tray icon `--background --no-tray`), then waits up to 15 s for a valid `api.json`. **Whether CaseHUD is controllable does not depend on the version number but on what it does:** if the process ends immediately with exit code 2 (unknown flag), the build counts as too old; it is started once with `--minimized`, and the interface shows "This CaseHUD version is too old – please update". If the `api.json` appears, it counts as controllable. The result is remembered per exe build (path + version + file modification time) in `casehud-capability.json` in CouchHUD's data folder, a new build is probed anew; "too old" applies for at most 7 days, after which it is probed again. A timeout without an exit alone does not make a build "old". The autostart entry (`--minimized` → `--background`) follows the same result: only a build recognized as controllable is rewritten to `--background`. All others (old or never probed) keep `--minimized`, so that an old build does not fail at boot with exit 2; a running CaseHUD with a valid `api.json` is noted as controllable, and the next start then uses `--background`. | `CaseHudDiscovery.cs`, `CaseHudCapability.cs` |
| API v1 on `127.0.0.1` with `X-Token` and a matching Host header, timeout 5 s, error format `{"error":{"code","message"}}`. The token appears in no log, no error text and no WebView URL. | `CaseHudClient.cs` |
| Live status via `/api/v1/events` (SSE) with reconnection (1, 2, 4 … 30 s). | `CaseHudEvents.cs` |
| **Lighting:** `GET /lighting` and `PATCH /lighting`. CaseHUD merges a PATCH (fields, parameters, devices and zones that are not sent stay) and answers with 200 and the full state as with GET; that state is adopted without another GET. So CouchHUD sends only what changes: one parameter, one device, and on an effect change only `effect` (CaseHUD then takes that effect's last values or its defaults). The host checks every change against the last state before it goes to CaseHUD: only known fields, brightness limited to 0–100, only a delivered effect, parameters of the current effect (with `effect` + `params` those of the new one) by their description (type, min/max, choice values, color exactly `#rrggbb`, lowercase), devices as an object by id `{"devices":{"<id>":{"disabled":true}}}` with nothing but `disabled` (never `settings`, `ignoreConflicts`, zones and segments). Text and unknown parameter types are never sent. Errors: 400 `bad_request` (with CaseHUD's reason; the host then rereads the state), 413 `payload_too_large`, 500 `internal` (device I/O, "please try again"), 401/403 `unauthorized`/`forbidden`, 405 become readable texts; 409 `ack_required` and 403 `gui_only` become a question whether to open the CaseHUD window. Responses are read with limits (at most 128 entries per list, texts at most 128 characters). | `CaseHudLighting.cs` |
| The host fetches preview images and passes them to the interface as a `data:` URL; the token stays in the host. | `CaseHudManager.cs` |
| **Game lease:** at game start `POST /gaming` (name, process ID, 120 s), renewed every 60 s, `active:false` at the end. | `CaseHudGamingLease.cs` |
| **Install and update:** latest release of `kewe87/CaseHUD` (GitHub API), download only from github.com over https, required: `SHA256SUMS.txt`, a valid signature and a matching SHA-256 of the setup. Only a release with a valid signature (the signature is checked even before the confirmation dialog) and minimum version 1.0.0 is offered; older or unsigned releases are neither installed nor offered as an update, and the interface shows "No signed CaseHUD version available yet". If the installed version cannot be read, there is no update notice; manual installation stays possible. An update means: signed, at least 1.0.0 and newer than the installed version (from 1.0.0 versions rise monotonically). If a release lacks the checksum file, it says "not verifiable" and **nothing** is installed. **Private or unreachable repository:** if GitHub answers the release query, checksums or signature with 404, 401 or 403 (no rate limit), the state is "Downloads currently unavailable" with one line in the log; automatically it asks again after 12 hours at the earliest (for a 403 without rate limit only 15 minutes; a single missing file during download sets no block), via "Check again" any time. The design gallery and community designs run through the CaseHUD API and are not affected; CouchHUD uses no raw links on `kewe87/CaseHUD`. Before that, when checking, the host issues a **one-time token** bound to exactly this release (tag, setup file, size); install and update accept only this token and abort if GitHub meanwhile delivers something else or the version is not newer than the installed one (downgrade). The dialog names version and changes and says "signed and verified"; there is no longer a question about a missing signature. Only in builds with an empty release key does the branch "unsigned, checksum only" remain (the one-time token still binds the confirmation to exactly one release). If the setup fails or UAC is declined, CaseHUD starts again if it ran before. Then `CaseHUD-Setup-x.y.z.exe /VERYSILENT /SUPPRESSMSGBOXES /NORESTART /TASKS="autostart,fps"` with UAC. Before an update `POST /quit` ends the running CaseHUD. Nothing is installed during a game. | `CaseHudRelease.cs`, `CaseHudManager.cs` |
| **Signature:** ECDSA P-256 over `"casehud-release-v1\n"` plus the bytes of `SHA256SUMS.txt`, file `SHA256SUMS.txt.sig`: one line of Base64 with a trailing LF (trimmed when checking), the signature itself in ASN.1 DER format (not IEEE P1363). The key is fixed in `CaseHudInfo.ReleasePublicKeyPem`; the SHA-256 over its SPKI DER bytes (fingerprint) is `cfb6863f23c892a53c93786dd1ee78478618aed680c5603fbc3955c1dde4abaf`, a test checks it. With the key set, the signature is mandatory (with an empty key only the SHA-256 would be required). The same verification code as for CouchHUD's own releases, with its own context and key, so a signature never counts for anything else. | `CaseHudIntegrity` |

Bridge methods (all prefixed `caseHud`): `Status`, `CheckUpdate`, `Start`, `Install`, `Update`, `OpenGui`, `Panels`, `PatchPanel`, `Designs`, `Sets`, `ApplySet`, `Scenes`, `ActivateScene`, `Rotation`, `NextScene`, `Power`, `Identify`, `Community`, `Import`, `Awtrix`, `Lighting`, `PatchLighting`, `Preview`. The host sends the `caseHud` event on every change.

## Privacy

See [PRIVACY.md](PRIVACY.md): local API (does not leave the PC) and fetching release information or the setup from GitHub, on request only.

## Without CaseHUD

If CaseHUD is not installed, nothing changes: the page only offers installation, and in the background CouchHUD at most checks whether an `api.json` exists.
